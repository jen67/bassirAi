BassirAI Project Architecture & Security Blueprint

System Architecture, Authentication, and Security Controls

1. System Architecture Overview

BassirAI is structured as a modular, multi-tenant SaaS application that isolates administrative control interfaces from the background AI automation pipelines.

Clinic Administrator / Staff
Next.js 16 Web Portal
Supabase Database / Auth
Patient (WhatsApp API)
n8n Automation Engine
Pinecone RAG Namespace

Core Core Architecture Modules

  • Next.js 16 (App Router / Turbopack): Serves as the management dashboard. All page structures utilize asynchronous server-side components to retrieve parameters, with high-fidelity glassmorphic clients for interactive tabs.
  • Supabase (PostgreSQL & Go-Auth): Manages authentication records, rows configuration schemas, clinics metadata, catalog prices, FAQs lists, and message tracking tables.
  • n8n Workflow Automation: Configured as the core communication webhook responder. Resolves inbound WhatsApp requests, checks auto-responder flags, queries RAG databases, and dispatches messages.
  • Pinecone Vector DB: Stores text embeddings representing clinic document knowledge folders. Every tenant is strictly isolated by matching searches to their specific pinecone_namespace.

2. Authentication Flow (Supabase SSR Cookie Auth)

To avoid client-side token vulnerabilities (XSS), BassirAI implements secure server-side session tracking via browser cookies.

Security Design

Instead of standard sessionStorage, Supabase session tokens are saved as HTTP cookies. A custom Next.js 16 edge proxy middleware intercepts browser requests and authorizes route access before page components are compiled.

Implementation Client Wrappers:

  • Browser Client (client.ts): Used for interactive form actions such as triggering credentials verification upon submission.
  • Server Client (server.ts): Handles server components. Utilizes async cookie stores to dynamically synchronize token states.
  • Admin Client (admin.ts): Created using the secure service role key to perform database actions bypass checks (e.g. provisioning profile link inserts during signup).

3. Row-Level Security (RLS) & Security Definer

Row-Level Security (RLS) is enabled on all tables in PostgreSQL. No database query can fetch or modify rows belonging to a different clinic.

The Recursion Challenge

Checking RLS user clinic IDs directly in a SELECT policy on the users table causes infinite loop execution errors. We resolved this by creating a lookup function running with database owner privileges (SECURITY DEFINER), bypassing RLS logic:

CREATE OR REPLACE FUNCTION get_user_clinic_id()
RETURNS UUID AS $$
BEGIN
    RETURN (SELECT clinic_id FROM users WHERE id = auth.uid());
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

Table Security Policies:

  • clinics: id = get_user_clinic_id()
  • users: clinic_id = get_user_clinic_id()
  • conversations: clinic_id = get_user_clinic_id()
  • messages: clinic_id = get_user_clinic_id()

4. Multi-Tenant RAG Schema & Language Translation

The backend and n8n layers are engineered to seamlessly scale with dynamic translation tools (such as the English/Arabic classifier your teammate is building).

Translation Integration Guide

  • Document Ingestion: Google Drive documents crawled via n8n split and embedding nodes are pushed strictly to a unique clinic namespace parameter.
  • Dynamic Webhook Resolution: The incoming WhatsApp text triggers the translator node. It determines if the patient prefers English or Arabic, retrieves the clinic customizations (e.g. FAQ Naira price tables) from Supabase, compiles system prompt templates, translates them, and feeds the localized parameters to the Llama model.
  • Takeover Gates: A boolean is_human_takeover flag exists in the database. The n8n automation webhook queries this before generating replies; if true, the AI responder remains silent to allow manual receptionist callback followups.
